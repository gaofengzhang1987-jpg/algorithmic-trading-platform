# 增量更新流水线

> 更新时间：2026-07-30
> 基于：[docs/全量更新流水线.md](docs/全量更新流水线.md)
> 适用场景：日线/周线/30min K 线已拉到目标日期，仅信号重生 + RPS + 管线

---

## 一、增量定义与设计约束

### 1.1 什么是"增量"

CZSC 的 `generate_czsc_signals` **没有增量 API**——每次调用都从给定 bar 列表从头重建结构（笔、中枢、信号），与上次运行结果无关。因此本流水线的"增量"定义为：

> **减少输入 bar 数量来提速，而非只更新有变化的部分。**

无论日线数据新增了 1 天还是 1 周的 bar，CZSC 都需要重算最后 N bar 的结构。新增 bar 数不影响单只耗时——`generate_czsc_signals` 时间 ∝ 传入的 bar 总数。

### 1.2 日更 vs 1 周后更新的差异

| 场景 | 新增 bar | max_bars 取值 | 单只耗时 | 全量耗时（4核） |
|------|---------|--------------|---------|---------------|
| 日更 | ~1 bar | 800 | ~2.0s | ~42 min |
| 1 周后 | ~5 bar | 800 | ~2.0s | ~42 min |
| 1 月后 | ~20 bar | 800 | ~2.0s | ~42 min |
| 全量 | 不截断 | 1583 | ~4.0s | ~65 min |

**结论**：不论过了几天，增量流程完全一样——因为耗时取决于截断后的 bar 总数，与新增多少 bar 无关。真正的提速来自 `max_bars` 截断。

### 1.3 `max_bars` 取值依据

CZSC 的 `init_n=300` 用前 300 bar 做结构初始化。剩余 bar 用于信号检测：

| max_bars | init_n | 信号检测 bar | 信号质量 | 建议 |
|----------|--------|------------|---------|------|
| 350 | 300 | 50 | ❌ 太少，信号不稳定 | 不用 |
| 500 | 300 | 200 | ⚠️ 可接受 | 日更应急 |
| **800** | 300 | **500** | ✅ 稳定 | **推荐默认** |
| 1200 | 300 | 900 | ✅ 稳定但慢 | 月更用 |

**推荐默认值**：日线 `max_bars=800`（约 3.2 年，足够覆盖一轮完整牛熊），周线 `max_bars=200`（约 4 年）。

### 1.4 与全量更新的差异总览

| 阶段 | 全量更新 | 增量更新（日线 800 bar） | 提速 |
|------|---------|------------------------|:---:|
| 上游数据拉取 | §0 三步 API 拉取 | 同全量 | — |
| 日线信号 | ~1583 bar, ~65 min | ~800 bar, **~42 min** | 1.5x |
| 周线信号 | 全量, ~5 min | ~200 bar, **~3 min** | 1.7x |
| 30min 信号 | L1 候选补缺, ~90 min | 同全量 | — |
| RPS | full/rebuild | refresh（已有增量） | — |
| 正式管线 | `run_zones.py 100` | 同全量 | — |
| struct_cache | CZSC 自动生成 | 同全量（截断 bar 不影响笔结构确认） | — |

## 二、增量信号重生实现

### 2.1 `signal_chunk.py` 新增 `--max-bars` 参数

在现有 `FREQ_MAP` 基础上，新增默认值：

```python
FREQ_MAP = {
    "日线":   {"data": "daily",  ..., "max_bars": 800},
    "周线":   {"data": "weekly", ..., "max_bars": 200},
    "30分钟": {"data": "min30",  ..., "max_bars": None},  # None = 不限
}
```

处理逻辑（在 `RawBar` 构造前）：

```python
if fm["max_bars"] is not None and len(df) > fm["max_bars"]:
    df = df.tail(fm["max_bars"])
```

`generate_czsc_signals` 调用时，`sdt` 改为最后第 300 bar 的日期（而非全量的 `20200101`）：

```python
sdt_date = df["date"].iloc[0].strftime("%Y%m%d")  # 截断后首日
sigs = generate_czsc_signals(
    bars, signals_config=sig_config,
    sdt=sdt_date, init_n=min(INIT_N, len(bars)), df=True,
    tqdm_kwargs={"disable": True},
)
```

### 2.2 `run_signal_parallel.py` 新增 `--incremental` 标志

```bash
python3 tmp_out/run_signal_parallel.py --incremental       # 日线增量
python3 tmp_out/run_signal_parallel.py --freq 周线 --incremental  # 周线增量
```

`--incremental` 标志透传给 `signal_chunk.py`，激活 `--max-bars` 截断。不带此标志时走全量路径，行为不变。

## 三、增量更新完整流水线

```bash
# 前提：日线/30min/周线K 已通过 l1_update.py 拉到目标日期

# Step 1: 日线信号增量（4 核, ~14 min）
python3 tmp_out/run_signal_parallel.py --incremental

# Step 2: 周线信号增量（4 核, ~3 min）
python3 tmp_out/run_signal_parallel.py --freq 周线 --incremental

# Step 3: 30min L1 候选补缺（4 核, --max-bars 2000, ~16 min）
#        内部自动：L1沉积 → 检查缺口 → 只生成缺的
python3 tmp_out/l1_30min_bridge.py --target-date 2026-07-24

# Step 4: 重建 daily_close +刷新 RPS
python3 -c "..."   # 重建 daily_close.parquet（见全量文档 §3.2）
python3 rps_calc.py refresh

# Step 5: 正式管线 L1→L4
python3 run_zones.py 100
```

总耗时估算（4 核）：**~42 + 3 + 16 + 2 + 5 ≈ 68 分钟**（vs 全量 ~65 + 5 + 90 + 2 + 5 ≈ 167 分钟，节省 ~59%）。

## 四、日常增量更新（高频场景）

若仅数据拉取后跑 RPS+管线、不重跑 30min 信号（30min 通常跨天不变）：

```bash
# 前提：日线 OHLCV 已增量拉到最新

# Step 1: 日线信号增量
python3 tmp_out/run_signal_parallel.py --incremental

# Step 2: 周线信号增量
python3 tmp_out/run_signal_parallel.py --freq 周线 --incremental

# Step 3: 重建 daily_close + RPS
python3 -c "..." && python3 rps_calc.py refresh

# Step 4: 正式管线
python3 run_zones.py 100
```

总耗时：**~42 + 3 + 2 + 5 ≈ 52 分钟**（vs 全量 167 分钟，3.2x 提速）。

## 五、设计约束

1. **`--max-bars` 必须可关闭**：默认 `None`（不限），仅 `--incremental` 时激活。全量路径行为不变。
2. **`sdt` 动态计算**：截断后取首日，不能用硬编码日期。
3. **CZSC 初始化不丢**：`init_n=min(300, len(bars))` 确保结构初始化有足够 bar。
4. **与全量幂等**：增量跑完的信号文件与全量跑完的结果应一致（`generate_czsc_signals` 截断输入但算法确定性相同）。
5. **30min 无增量**：30min bar 数通常不超 2000，`--max-bars` 不生效（`FREQ_MAP["30分钟"]["max_bars"] = None`）。
